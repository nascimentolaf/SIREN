    Known issues#

    What is inconsistent or easy to trip over in the code as shipped. The documentation describes the code as it behaves; this page lists where that differs from what one would expect.

    Limitations#

    Issue Where Effect
    Every siren process holds one Gurobi license token for its whole run run_paper_experiment.sh, siren with a license limited to W processes at once, the workers of all machines together must stay within W; a siren started beyond it exits with status 1 and its pair is marked fail (rerun to retry)
    The analysis stage needs the default OUTPUT_DIR run_paper_experiment.sh plot_paper.py reads output/sweep/; a run in another output tree can run every stage but analysis
    sweep_experiment.sh --collect writes into the repository's analysis/csv/ sweep_experiment.sh whatever OUTPUT_DIR says; collect another tree with analysis/collect_verdicts.py directly
    The flowset shuffle uses std::shuffle, whose algorithm is implementation-defined generate_flowset/src/main.cpp the same FLOWSET_SEED can draw a different batch with another C++ standard library
    RQ4's period tie-break depends on the Python version stretch_periods in rq4_hyperperiod.py among the period assignments with the same largest stretch, prepare keeps the one of smallest sum(ratios), a float sum, and Python 3.12 changed sum() of floats to compensated summation. With Python 3.10 or 3.11, prepare writes exactly the models of results/rq4_models/; with Python 3.12 or later, 71 of the 4816 get other periods, with the same largest stretch and the same exact sum of ratios, so equally valid
    The two servers of the paper's run differ at large models rq4_regression.json (servers), the paper's RQ4 the servers are identical, yet for a given flowset the large models ran slower on one of them: by about 0.3 % at H* = 420 ms and about 15 % at 25 200 ms (slower_over_faster_same_flowset). RQ4's intervals cover the flowsets, not the machine, so rq4_statistics.py also fits each server alone; the growth stays nearly linear on both

    Code that names programs not in this repository#

    Some code refers to other tools, which this repository does not include:

    • analysis/rq4_hyperperiod.py run --solver defaults to a solver binary that is not shipped: always pass --solver offline_phase/siren/siren, as run_paper_experiment.sh does.
    • scripts/sweep_experiment.sh without --collect runs a sweep through a script that is not shipped, and fails; only --collect is used.
    • scripts/parameters.sh defines settings that no shipped script reads (METHOD_VARIANTS, whose default names a baseline that is not shipped; REUSE_FLOWSETS, CLEAN_OUTPUT; the paths of other tools); see Configuration.
    • analysis/plot_paper.py --partial --copy runs a script that is not shipped; run_paper_experiment.sh does not use it.
    • The analysis code knows the methods edf, 5gtps and 5gtps_harq (labels, colours, macros). Runs of this repository have no such rows.

    Equation numbers in the code#

    Comments and a few messages in the code number the paper's equations differently from the paper. To read them:

    In the code In the paper What
    Eq. (2) Section V-A segments per packet, N
    Eq. (3) Eq. (1) per-TB error target, E^tb
    Eq. (4) Eq. (2) attempts, A
    Eq. (5) Section V-C worst-case time C, and the check C + t_up <= D
    Eq. (6) Eq. (3) Pareto set, P_i
    Eqs. (7) to (10) Eqs. (4) to (7) the ILP's constraints
    Eqs. (11), (12) Eq. (8) the harq objective
    Eqs. (13), (14) Eq. (9) the rb_peak objective

    The code's baseline_algorithms/must/ and baseline_algorithms/qospf/ also cite the equations of the MUST and QoS-PF papers, as their pages do.

    Behaviours to keep in mind when reading results#

    These are deliberate, but change how a verdict reads.

    • Baselines can exceed A^max. They select from the unscreened configuration set, within A^max whenever a configuration within it fits the cell; where none does they fall back to more attempts, and plot_paper.py reclassifies such runs as ko_amax (the raw CSVs do not). On the shipped catalogue and MCS table no application needs the fallback, at any budget. See Baselines.
    • The ILP's per-candidate cap is wall-clock time. A candidate near the 60 s cap may be decided on one machine and not on another, or under another load. run_paper_experiment.sh pins each worker to its own physical core for this reason. Every ILP log names its machine (Host:), and plot_paper.py --derive carries it into the timing table (host). The baselines are deterministic and do not depend on the machine.
    • ILP counts depend on the budgets: how many tables, how many candidates tested. See Analysis.
